# 0032. Tenant moves and regions

- Status: Accepted
- Date: 2026-11-24
- Related: [ADR 0010](0010-logical-sharding-region-residency.md), [ADR 0023](0023-identity-data-routing.md), [ADR 0024](0024-typeorm-persistence-sharding-persistent-sagas.md), [ADR 0031](0031-reports-billing-identity-sagas.md)

## Context

The F10 design sets the regions (`REGIONS`, `SERVICE_REGION`, `PLATFORM.SHARDING.WRONG_REGION`), the `@platform/tenant-move` library with two copy strategies and two write gates, and the `MoveTenant` saga. Building them exposed gaps: each service has its own shard directory in its catalog and only identity placed tenants, so the other services did not know about a new tenant nor could they move it; a gate read from a cache does not guarantee that no write reaches the source late; and the saga's log cannot live in the shard of the tenant being moved.

## Decision

- **Regions.** `@platform/service` reads `REGIONS` (code, `apiBaseUrl` and `issuer`) and `SERVICE_REGION`, hands them to the router and exposes `ServiceRegions`. A tenant from another region answers 421 with `details.apiBaseUrl` and `details.region`: the error catalog declares per code which data are public (`publicDetails`) and the mapping to Problem Details publishes only those. Identity answers `sign-in` with its region and its `apiBaseUrl`. The `issuer` is used: with `SERVICE_REGION` declared, the configuration does not start if `AUTH_ISSUER` is not the `issuer` of that region, so a token issued in another region does not verify (its `iss` is different). Identity does not start if `IDENTITY_REGION` differs from `SERVICE_REGION`, nor if `REGIONS` declares regions and `SERVICE_REGION` is missing: without it the router does not reject the tenants of another region.
- **Move configuration.** `TENANT_WRITE_GATE` and `TENANT_MOVE_MAX_WAIT_MS` (5 s by default, how long a write waits with the gate closed) are the `tenant-writes` section of `@platform/service`, validated with zod. The gate is chosen when composing the modules, before the context exists, so the runtime validates that section with the same schema at that point.
- **Tenant directory in each service.** Identity chooses where a tenant lives and the other services record it in their own directory with the same region and the same shard group. `defineTenantDirectoryOperations(service)` declares `<service>.tenant-directory.place.v1` (idempotent: if the row already exists it leaves it as it is, because a later move may have changed it) and its reversal `<service>.tenant-directory.remove.v1` (no compensation: it removes the row before the tenant has data), and `TenantDirectoryModule.forFeature({ service, operations })` from `@platform/tenant-move` registers them in tasks, notifications, reports and billing, as `TenantMoveModule` registers the move operations. Both write with the directory's conditional write (`putPlacement` and the new `deletePlacement` of `DirectoryWriter`, which deletes only if the version did not change) and invalidate the router. An unconfigured group or a shard the service does not have answers `PLATFORM.TENANT_MOVE.UNKNOWN_TARGET`, and a group that clashes with a dedicated tenant `PLATFORM.TENANT_MOVE.SHARD_TAKEN`. They are internal codes of `@platform/tenant-move`, which the contract does not declare, like those of the move operations: they reach the saga as a protocol violation with the code, and before the pivot the saga compensates including that step, whose reversal finds no row and answers the same.
- **Shard groups.** `TenantShardGroups` translates between a service's logical shards and the groups they all share: the group declared in `TENANT_MOVE_TARGETS` (the same one moves use) takes precedence and, without it, a shard's group is its name without the service prefix (`identity_shard_1` and `tasks_shard_1` are group `shard_1`). That way a single-region deployment with the naming convention of `init.sql` and Terraform configures nothing, and one with several regions or with its own names declares each shard in `TENANT_MOVE_TARGETS` of each service.
- **Where a tenant is born.** There are two paths and both place the tenant in the other services. `POST /v1/tenants` starts `TenantOnboarding` with the placement identity chose, and the saga runs the placement in tasks, notifications, reports and billing after creating the tenant and before opening the billing account, all before the pivot and with its reversal. The region's two fixed tenants (the platform tenant and the shared customer tenant, which occupies all shards) do not go through the saga: `SeedRegionTenants` places them in the other services with the same operations, so identity's seeding runs after deploying the others and can be repeated. User sign-up does not create tenants: whoever signs up without an invitation lands in the shared customer tenant, and whoever arrives invited in the tenant that invited them. `identity.tenants.create.v1` is only called by the onboarding saga.
- **Five operations per service.** `defineTenantMoveOperations` adds `switch` to `sync`, `finalize`, `abort` and `cleanup`: each service points its own directory to the target after the pivot, because the directory lives in each service's catalog. `TenantMoveModule.forFeature({ operations, manifest, listener })` registers them; identity's listener points the catalog indexes (slug, emails, passkeys and API key prefixes) to the new region and records the move.
- **Two pieces to stop writes.** The gate (`TenantWriteGate`, in the directory with the placement in `Migrating` or in Valkey, depending on `TENANT_WRITE_GATE`) makes a write wait up to `writeWait` and then answers `TENANT_MIGRATING` with `Retry-After`. The shard fence (`tenant_write_fences` and a shared per-tenant advisory lock that every write transaction takes before opening) provides the guarantee: `finalize` writes the fence and takes the exclusive lock, which waits for the transactions already inside; from then on no write of the tenant reaches the source and the last round copies everything committed.
- **Lifetime of the fence.** The source fence stays until `cleanup`, to stop a process that still has the old placement in cache; `cleanup` deletes the data and then lowers it. `switch` marks it as pivoted (`switched_at`) and lowers the one a previous move left on the target, because the tenant can return to a shard it left; if it returns before the cleanup of the first move, that cleanup no longer finds its fence and does not touch the live rows. Raising a fence that already exists hands it over to the new move.
- **Cross-tenant maintenance.** `TenantMaintenanceSession` takes a shared per-shard lock that `finalize` also waits for, and fails with `TENANT_MIGRATING` if the shard has a move that has not pivoted: periodic maintenance repeats it on the next run, and one-off tasks (deleting a user's data in tasks and reports) fail with `requireEveryShard` so the saga repeats them. Its queries leave out the rows of tenants that have already left (`TenantWriteFence.unfenced`). Maintenance of the `login_attempts` partitions does not go through it: it drops old partitions by date, the same on the source as on the target.
- **Region in the rows.** A manifest table can declare `regionColumn`; `switch` changes it to the target region in the copy before pointing the directory. Identity declares it on `tenants`: after the switch, the process in the source region no longer reaches the target shard through routing, so its listener only updates the catalog indexes.
- **Copy.** `BatchTenantDataTransfer` (the default) copies by key, repeats delta rounds by `updated_at` with a margin and, with the tenant frozen, compares the count and the sum of `md5` (computed over the columns the copy writes in name order, not over the whole row, because the physical column order can differ between source and target) and reconciles in ranges of `TENANT_MOVE_BATCH_SIZE` rows the table that differs, rewriting only the ranges that differ. The verification progress is kept in `tenant_move_checkpoints` on the target (verified tables and the last reconciled key), so a table that does not fit in one call's deadline finishes over several; it is deleted when everything is verified or on abort. `LogicalReplicationTransfer` uses a publication filtered by tenant and a subscription that applies with its own role (`run_as_owner`), which must bypass RLS; it only works for manifests with a tenant column on every table, so with `TENANT_MOVE_STRATEGY=logical` a manifest with `via-parent` tables (identity) still goes by batches. With logical replication, copying the service's tables and copying the platform's tables are two parts of `CompositeTenantDataTransfer` that spend a single `TENANT_MOVE_CALL_BUDGET_MS` budget per call (`TransferBudget` travels in the `TenantTransfer`), so no call lasts longer than that budget. The tables stay with `REPLICA IDENTITY FULL` while any publication includes them: creating and dropping publications takes a shard lock and the identity goes back to normal only when no publication still has the table, so that two moves from the same shard do not step on each other. Changing the identity takes an `ACCESS EXCLUSIVE` lock on the table; it is requested with `lock_timeout` (`TENANT_MOVE_LOCK_TIMEOUT_MS`, 2 s by default) and, if it does not arrive, the round answers `RoundPending` and the saga repeats it, instead of queuing every write to the table behind the lock.
- **Platform tables.** `PlatformTenantMoveManifest` declares the platform tables with tenant data that travel with it, and the copy adds them to each service's manifest, always by batches (the step log reaches the tenant through its saga, and logical replication does not filter by a parent): `idempotency_keys`, which stores in `tenant_id` the tenant of the call (migrations `1794800001004` on the shards and `1794800001103` on the catalog), `processed_messages`, which stores in `tenant_id` the tenant of the message envelope (migration `1794800001005`; `ClaimGuard` fills it when taking the claim of the delivery), and `saga.instances` with `saga.step_log`. That way a retry with the same idempotency key after the switch answers what was stored instead of repeating its effects on the target, a message the source already processed that arrives again after the switch is recognized as a repeat on the target, and the state of a tenant's saga can still be queried from its shard. Services with `requireScope` (the template's five) store the internal API keys in the catalog, which is a single one for all regions, and those do not need to travel.
- **Sagas in progress.** A tenant saga that is running, waiting for a retry or compensating on the source would keep writing there after the last round. `sync` answers `RoundPending` while the tenant has one on the shard (the move saga repeats until they finish), and `finalize`, with the fence already raised, fails with `TENANT_BUSY` (not retryable) if one appeared: the move saga is compensated and launched again once they finish. A saga that requires intervention does not stop the move and travels as history.
- **Saga.** `MoveTenant` runs `sync` and `finalize` in identity, tasks, notifications, reports and billing (compensated with `abort`), the pivot, `switch` in the same order and finally `identity.tenant-moves.finish.v1` (`FinishMove`), which records the move as switched. Only that last step moves it to `Switched`: identity's `switch` is the first of five, and if another service's gets stuck, its source stays alive. Its log lives in the shard of the platform tenant. `tenant_moves` in identity's catalog stores the move. It is launched with `nx run identity:tenant-move -- --tenant=<id> --target=<group>`: the `TENANT_MOVE_TARGETS` group already states its region.
- **Cleanup.** `TenantMoveCleanupJob` runs every hour and takes up to 20 moves switched more than `TENANT_MOVE_GRACE_DAYS` ago, first those never attempted and then those that have gone longest without an attempt (`cleanup_attempted_at`), so the ones that always fail do not block the new ones. For each service it repeats `cleanup` while it answers `RoundPending`, with a new key per attempt (a fixed key would return a stored result) and a pause of `TENANT_MOVE_CLEANUP_PAUSE_MS` (1 s by default) between attempts so as not to load the shard without respite, up to `TENANT_MOVE_CLEANUP_MAX_ATTEMPTS` attempts (30 by default), two minutes per service and move and fourteen per run; a failure in one service does not prevent trying the others, and the move is left for the next run until all of them finish. As a safeguard, `cleanup` fails with `NOT_SWITCHED` (not retryable) if the service's directory still points the tenant to one of the shards it was going to delete.
- **Rounds, deadline and transient failures.** `sync` and `finalize` declare `RoundPending` as progress (`progressOn`): a pending round does not spend the saga's suspensions, which are kept for real failures. The saga starts with the deadline `TENANT_MOVE_DEADLINE_MS` (6 h by default); if it expires before the pivot, it compensates and the tenant writes to the source again instead of staying frozen. A foreign key that fails on the target during a round (a child row written after the round copied its parent table) answers `RoundPending`, and a transient Postgres error in the internal API server is `transient-failure` and not `protocol-violation`, thanks to the service's failure classifier.
- **Tables without `updated_at`.** The `sync` rounds only copy the new rows of a table without `updated_at` (`login_attempts`, `saga.step_log`, `user_tenants`, `recovery_codes`); their updates and deletes are fixed by the range reconciliation of `verify`, which stores its progress in `tenant_move_checkpoints`. Rereading it in full on every call always used up the deadline on it.
- **Abort.** `abort` lowers the fence and opens the gate before purging the target: the tenant writes to the source again while a copy nobody reads is discarded.
- **Cleanup with a move in progress.** `cleanup` fails with `MOVE_IN_PROGRESS` if another move of the tenant has its fence raised without having pivoted, and `TenantMoveCleanupJob` skips tenants with a move in progress. A tenant can return to the shard its previous move has not cleaned up yet: between the `finalize` and the `switch` of the return, that shard already holds the good copy and the old cleanup would delete it.
- **Minimum grace.** `TENANT_MOVE_GRACE_DAYS` is at least 1. With zero, `cleanup` would lower the source fence while a process with the old placement in cache can still write there.
- **Removing a tenant from the directory.** `tenant-directory.remove.v1` fails with `TENANT_HAS_DATA` if the tenant already has rows in the tables of the service's manifest (not in the platform's, which it has had since its onboarding) and with `MOVE_IN_PROGRESS` if its gate is closed by a move. It is the reversal of the onboarding, before the tenant has data; without the check, a late compensation would leave orphan rows.
- **User data.** Notifications stores `home_tenant_id` in the inbox and the preferences, as the deliveries already did, so that its manifest selects the rows of the tenant's users.

## Consequences

### Positive

- No row committed during the move is lost or duplicated, with either of the two gates (tested with two PostgreSQL and two Valkey instances), and a tenant can return to the shard it left.
- Each service tests its manifest on its real migrations: it seeds each table, moves, compares count and sum per table and cleans up the source without touching the neighbour.
- Each service remains the owner of its directory and its data, and knows each tenant from its onboarding, so it can serve it, open an account for it and move it.

### Costs

- Each write transaction takes and releases an advisory lock and reads `tenant_write_fences`. With `TENANT_WRITE_GATE=valkey` it also adds an `EXISTS` to Valkey; a short local cache would avoid it, but the guarantee is still the shard fence. If releasing the lock fails, the connection is closed instead of going back to the pool.
- While a move is halfway through on a shard, that shard's maintenance tasks wait for the next run.
- Idempotency keys and processed messages older than their migrations (`1794800001004`, `1794800001103` and `1794800001005`) have a null `tenant_id` and do not travel: they cover a retry or a redelivery only until their retention TTL, and only on the source shard. After that period they no longer exist on any shard, so a deployment with older data can move without backfilling the column; during the period, a retry or a redelivery that lands on the target is processed again, and consumers tolerate it because deliveries are already at least once.
- `outbox` is not moved: the source relay publishes whatever was left pending, because it does not depend on the tenant, and retention deletes it.
- Inbox and preference rows older than `home_tenant_id` are neither moved nor cleaned up: they stay on the source. The template had no deployments with data; a deployment with old data must backfill the column from identity's `user_tenants` before moving.
- `audit_log` is neither moved nor cleaned up: it is insert-only (a trigger rejects `UPDATE` and `DELETE`) and its retention detaches partitions by month. The history before the move stays on the source shard until its partition expires; on the target it starts with the inserts the copy itself makes. A deployment that requires no data to remain in the source region must export and detach those partitions by hand.
- A tenant with a long saga in progress cannot be moved until it finishes.
- The target region learns about the switch when its router's cache expires, because each region has its own change channel.
- A round that does not catch up with the source is retried with the saga's backoff; a tenant that writes faster than a round copies needs a higher `TENANT_MOVE_CAUGHT_UP_ROWS`. If it does not catch up within `TENANT_MOVE_DEADLINE_MS`, the move is aborted.
- The changes to a table without `updated_at` reach the target only in `verify`, with the tenant frozen: such a table that changes a lot lengthens the freeze.
- With `REPLICA IDENTITY FULL`, each `UPDATE` and `DELETE` of a published table writes the full old row to the WAL while the publication lasts, for all tenants on the shard and not only the one being moved; the WAL and the network to the target grow accordingly. The publication is dropped in `finalize` or `abort`, and a move abandoned halfway keeps it until its `abort`.
- Cleaning up a very large tenant can take several runs of the job.
- Tenant onboarding adds four internal calls and identity's seeding depends on the other services being deployed. A new service must be added to identity's `TenantDirectoryFollowers`; the generator reminds you.
- A deployment that neither follows the `<service>_shard_<n>` convention nor declares its groups cannot onboard tenants: the placement answers `UNKNOWN_TARGET` and the saga is compensated.
- Tenants that already existed in a deployment prior to these operations are not in the other services' directories; they are placed by calling `<service>.tenant-directory.place.v1` with their region and their groups, as the seeding does.

## Alternatives considered

- Copying identity's directory to the others through SQL or replication: it crosses catalogs of different services, and the shard-to-instance map is keyed by the name of each service's logical shard.
- A single catalog for the five services: in a move each service points its own directory to the target, and each is deployed separately.
- Having each service learn about the tenant from `identity.tenant.created.v1`: it arrives after the saga opens the billing account, which needs the tenant in its directory, and it is not compensated if the onboarding is undone.

- Relying only on the gate: a process with the placement in cache could write to the source after the last round.
- A separate `FreezeTenant` step in the saga: each service freezes its own directory in `finalize`, which is where it is needed.
