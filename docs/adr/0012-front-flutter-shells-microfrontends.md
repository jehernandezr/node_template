# 0012. Flutter front with shells and microfrontends

- Status: Accepted
- Date: 2026-11-11
- Updated: 2026-11-14 (SDK generated with `contracts_gen`, in-house Nx plugin and `shell_host`)

## Context

The platform needs clients for mobile, web and backoffice. Writing each domain twice, once for web and once for mobile, multiplies the work and leaves the contracts out of sync.

## Decision

Flutter for mobile, web and backoffice, with the SDK, contracts, authentication and widgets shared in Dart. The whole client lives in `front/`.

- Two shells: `front/apps/web` and `front/apps/mobile`. Both compose the same microfrontends per domain. What they share (session, login, step-up, shell pages, router and root app) lives in `front/packages/shell_host`; each shell contributes only its manifests, its navigation frame and its connection.
- Each microfrontend declares in its manifest its id, platforms, routes, menu (label, icon and badge), access rule, flag, modes it serves and links it accepts. Microfrontends depend only on `front/packages`, the shared packages do not know any microfrontend, and they communicate through the shell's event bus (each one declares its events) and through routes.
- The web app loads microfrontends lazily according to the profile, so a customer never downloads the backoffice.
- The contracts' Dart (types, validators, routes and codes) is generated by `front/tools/contracts_gen` from the `contract.json` that `backend/libs/contracts` exports (ADR 0017), and changes in the same PR as the backend. The HTTP client is `ApiClient` from `front/packages/api`, on `package:http`.
- Nx orchestrates the workspace with an in-house plugin (`front/tools/nx-plugin`) that registers each member of the pub workspace as a project, with its `analyze`, `format-check` and `test` tasks.

## Consequences

Positive:

- A domain is written once and appears on web and on mobile.
- A contract change reaches the clients in the same PR.

Costs:

- The whole client is in Dart. A backend team working in TypeScript does not share a language with the front.
- The Nx plugin for Flutter is in-house and has to be maintained.
- The interface hides what the user cannot use, but the real security lives in the API.

## Alternatives considered

- A domain deployed separately on web: it is published as a Flutter app embedded in the shell, with the same contract.
- A public website that needs search engine ranking: the marketing pages go in a separate static site.
- A screen with its own version per platform: it is declared with `PlatformScreen` instead of duplicating the microfrontend.
