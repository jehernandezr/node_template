Two Opus auditors reviewed `main` (commit 13f606f) looking for violations of the repository guidelines, hexagonal architecture and clean code, overengineering, shortcuts, AI-style comments and bad practices. It is not an audit of plan compliance.

#### BE-02 · High · Hexagonal architecture (contract between infrastructure and runtime) · Terraform and the libraries do not speak the same configuration contract

- Paths: `backend/infra/terraform/stacks/service/main.tf:33-53`, `backend/libs/platform/adapters/aws/src/lib/aws-config.ts:31`, `backend/libs/platform/adapters/valkey/src/lib/valkey-client.ts:108-131`, `backend/infra/terraform/modules/valkey/main.tf:74-86`, `backend/libs/platform/adapters/valkey/src/lib/bloom-keys.ts:6`, `backend/libs/platform/adapters/valkey/src/lib/valkey-shard-directory-channel.ts:17`, `backend/libs/platform/adapters/valkey/src/lib/valkey-cache.ts:33`, `backend/.env.example:17-38`.
- Evidence:
  - `awsConfigSchema` requires `AWS_ACCOUNT_ID: z.string().regex(/^\d{12}$/…)` without a default value, but `base_environment` of the `service` stack only passes `SERVICE_NAME`, `DEPLOY_ENVIRONMENT` and `MESSAGING_NAME_PREFIX` (plus DB, Valkey and files). Neither Lambda nor Fargate injects `AWS_ACCOUNT_ID`, so the first deployed service that uses `@platform/adapters-aws` fails when validating its configuration at startup.
  - Terraform creates the Valkey users with `authentication_mode { type = "iam" }` and provides `VALKEY_HOST`, `VALKEY_PORT`, `VALKEY_USER`. `createValkeyClient` only receives `url` (`redis://` or `rediss://`) and neither generates nor renews the IAM token (SigV4, 15 minutes). With the current client there is no way to authenticate on AWS.
  - The Terraform ACL is `on ~<service>:* &<service>:* +@all -@dangerous` (Terraform README), but the adapters' default values do not comply with it: `keyPrefix ?? ''` in the cache and the routing cache, `DEFAULT_BLOOM_KEY_PREFIX = 'bloom'` and `SHARD_DIRECTORY_CHANNEL = 'platform:sharding:directory-changed'`. With the default values every command gets `NOPERM` on AWS and works locally, where there is no ACL.
  - Local and AWS use different names for the same thing: `.env.example` documents `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_CATALOG_NAME`, `VALKEY_URL`; Terraform provides `DB_PROXY_HOST`, `DB_READER_HOSTS`, `DB_DATABASES`, `DB_CREDENTIALS`/`DB_SECRET_ARN`, `VALKEY_HOST/PORT/USER/KEY_PREFIX`. No library reads `DB_HOST`, `DB_CATALOG_NAME`, `VALKEY_URL` or `SMTP_HOST` today (grep with no results in `backend/libs`). ADR 0020 says "AWS and local use the same databases, queue names and filters", but the variables do not match.
- Fix: before F4, define a single deployment configuration schema (in `@platform/config` or in each adapter) with the names Terraform provides, and make `.env.example` and `docker-compose.yml` use those same names. In Terraform, pass `AWS_ACCOUNT_ID` (or the exact ARNs and URLs of topics and queues from `local.messaging`, which already has them, and remove ARN construction from the adapter). In the Valkey adapter, accept `host`, `port`, `user` and a credentials provider that generates the IAM token and renews it on every reconnection. Make the key and channel prefix mandatory, derived from `SERVICE_NAME`, instead of default values the ACL rejects. Add a `terraform test` that compares the stack variables with the schema exported by the library.

#### BE-03 · High · Hexagonal architecture (dependency in the wrong direction)

`@platform/messaging` and `@platform/internal-api` depend on `@platform/persistence` to type the transaction port. `persistence` brings `typeorm`, `pg`, `@platform/sharding` and `@platform/criteria` at runtime (`persistence/package.json`), so any consumer of the bus or the internal client drags in TypeORM and the Postgres driver, and the messaging library ends up coupled to the persistence one.

- `messaging/src/lib/bus/outbox-message-bus.ts:2` `import type { TransactionManager, UnitOfWork } from '@platform/persistence'`
- `messaging/src/lib/outbox/outbox.ts:1,91` `append(record: OutboxAppend, uow: UnitOfWork)`: the outbox port receives the concrete `UnitOfWork`, which exposes `session: SqlSession` (`persistence/src/lib/transaction/transaction-manager.ts:17`). The messaging port leaks the adapter's SQL session.
- `messaging/src/lib/outbox/in-memory-outbox-store.ts:2`
- `internal-api/src/lib/router.ts:14` `import type { TransactionManager } from '@platform/persistence'` and the dependency in `internal-api/package.json` and `tsconfig.lib.json:17`.

Fix: move `TransactionManager`, `UnitOfWork` (without `session`) and `TransactionHook` to `@platform/kernel` (or `primitives`) as pure ports; `persistence` implements them. `OutboxWriter.append` must not receive the unit of work: the Postgres adapter takes it from the context (`transactions.current()`), as `PostgresIdempotencyStore` already does. Remove `@platform/persistence` from the dependencies of messaging and internal-api.

#### BE-04 · High · Hexagonal architecture / correctness · `ShardKey.User` routes by the actor, not by the user

- `backend/libs/platform/persistence/src/lib/context/persistence-context.ts:41`: `actorId: ctx.actorId ?? ctx.userId,`
- `backend/libs/platform/persistence/src/lib/sharding/database-resolver.ts:103`: `{ tenantId: context.tenantId ?? '', userId: context.actorId },`
- `backend/libs/platform/observability/src/lib/request-context.ts:26`: "End user. Matches `actorId` when `actorType` is `User`."

What is wrong: `RequestContext` distinguishes `actorId` (who executes: user, service account, API key, system) from `userId` (the end user). `PersistenceContext` has no `userId` and the resolver passes the actor as the user key. When a service account, a saga or a job acts on a user, the operation is routed by the service account's id and lands on another logical shard, without error. With identity sharded by user, that means empty reads and writes to the wrong shard.

Fix: add `userId` to `PersistenceContext`, copy it from `ctx.userId` in `requestContextProvider` and use `context.userId` in `routingKeyFor`. Test: a context with `actorType: ServiceAccount`, `actorId: S`, `userId: U` must resolve the shard of `U`.

#### BE-05 · High · Overengineering / dependencies · TypeORM halfway: two paths for connection, migrations and table definition

- `backend/libs/platform/persistence/src/lib/connection/typeorm-connection.ts:38`, `connection/pg-pool-connection.ts:51`
- `backend/libs/platform/persistence/src/lib/migrations/sql-migration.ts:43` (`toTypeOrmMigration`) and `:72` (`applyMigrations`)
- `backend/libs/platform/persistence/src/lib/repository/table-definition.ts:100` (`tableFromTypeOrm`)
- `backend/libs/platform/persistence/src/lib/repository/base-repository.ts:95-98`
- `docs/adr/0009-rds-postgresql-capa-persistencia-propia.md:13,17`

What is wrong: `BaseRepository` writes all its SQL by hand on top of `SqlSession` and does not use TypeORM anywhere. TypeORM only appears as three optional adapters, each with its own twin: `TypeOrmConnection` versus `PgPoolConnection`, `toTypeOrmMigration` versus `applyMigrations`, `tableFromTypeOrm` versus the hand-written `TableDefinition`. The repository JSDoc promises something else (`export class TypeOrmTaskRepository extends BaseRepository<Task, TaskOrmEntity>`) and ADR 0009 says "own layer on top of TypeORM" with `migration:generate`, which cannot work without real TypeORM entities. In production no code uses `applyMigrations` (only tests), and that runner takes no lock: two Fargate tasks that start together apply the same migration at the same time; in addition the `ROLLBACK` in the `catch` (`sql-migration.ts:103`) can throw and hide the original error. Identity (F4) is about to write its repositories and will have to choose one of the two paths without guidance.

Fix: decide on a single path and record it in ADR 0009. The option consistent with the code and with the preference for building in house is to remove `typeorm` from the library: keep `pg`, `TableDefinition` and `applyMigrations`, adding a `pg_advisory_lock` around the cycle and a guarded `ROLLBACK`. If TypeORM is kept, it must be the only route (migrations and metadata) and the twins get deleted. In either case, fix the JSDoc example.

#### BE-07 · Medium · Repo guidelines / Clean code · Platform error codes are written with three conventions and a test that reads files from another project keeps them in sync

- `backend/libs/contracts/platform/src/enums/platform-error-code.enum.ts:6-114` (`PlatformErrorCode`, the source exported to the front)
- Own enums that repeat the same text by hand: `platform/cache/src/lib/errors.ts:5`, `platform/config/src/lib/errors.ts:5`, `platform/sharding/src/lib/errors.ts:5`, `platform/bloom/src/lib/bloom-error.ts:4`, `platform/primitives/src/lib/errors.ts:5`, `platform/adapters/valkey/src/lib/valkey-error.ts:5`, `platform/resilience/src/lib/errors.ts:5`, `platform/criteria/src/lib/enums.ts:37`, `platform/kernel/src/invalid-id.error.ts:4` (all under `backend/libs`). Example: `InvalidArgument = 'PLATFORM.CACHE.INVALID_ARGUMENT'` in `cache` and `CacheInvalidArgument = 'PLATFORM.CACHE.INVALID_ARGUMENT'` in the contract.
- Frozen object that points to the contract: `platform/messaging/src/lib/errors/messaging-error.ts:11` (`InvalidEnvelope: PlatformErrorCode.MessagingInvalidEnvelope`), with a comment explaining that the enum is avoided because of `isolatedModules`.
- Direct use of the contract with a union type: `platform/persistence/src/lib/errors.ts:6-13`.
- `backend/libs/contracts/platform/src/errors/platform-error-catalog.spec.ts:75-88`: the test walks the disk from `join(__dirname, '..', '..', '..', '..', 'platform')` and searches for `'PLATFORM\.[A-Z_]+\.[A-Z_]+'` with a regex to detect codes missing from the catalog.

What is wrong: the same code exists twice in nine libraries, and the only safety net is a test in the contracts package that reads the source code of other projects through a relative path. That test does not run when only `platform/cache` changes (Nx does not mark it as affected, because `contracts` does not depend on `cache`), it only detects three-segment codes between single quotes and it does not detect a contract code that nobody throws anymore. CLAUDE.md asks for enums for errors; having three different ways of declaring them is exactly what that rule wants to avoid.

Since `type:platform` can depend on `type:contracts`, each library uses `PlatformErrorCode` directly (with a union type per library, as `persistence` does) and the duplicated enums and the `messaging` object are deleted. With that the file-reading test is no longer needed; if orphan codes should be detected, make it a lint rule (`no-restricted-syntax` on `'PLATFORM.` literals) that runs in every affected project.

#### BE-08 · Medium · Hexagonal architecture / Repo guidelines · The contracts declare every shape twice, by hand and in zod, and the check does not detect drift

- `backend/libs/contracts/identity/src/types/auth.type.ts:3-50` (interfaces `SignInRequest`, `SessionTokens`, `PendingMfa`...) and `backend/libs/contracts/identity/src/schemas/auth.schema.ts:46-58` (`SignInRequestSchema = z.strictObject({...}) ... satisfies z.ZodType<SignInRequest>`); the same in `types/session.type.ts` versus `schemas/session.schema.ts`, and in `contracts/platform` (`types/money.type.ts`, `types/pagination.type.ts`, `types/problem-details.type.ts` versus their schemas).
- `docs/adr/0015-estructura-backend-front-y-codigo-compartido.md`: the tree says `types/ # tipos e interfaces (incluye z.infer de los esquemas)`, but the rules table says `types` only imports `enums` and `constants`, so `z.infer` is impossible and the double declaration is mandatory.

What is wrong: every contract request and response is written twice. `satisfies z.ZodType<T>` only checks that the schema output is assignable to `T`; if someone adds an optional field to the interface and forgets the schema, or any field to the schema and forgets the interface, the compiler says nothing (only a new mandatory field in the interface fails) and the `contract.json` that reaches the front comes from the schema, not from the interface. In addition the ADR contradicts itself and does not mention the `errors/` and `kit/` folders that do exist in `contracts/platform` and `contracts/identity`.

Fix: invert the direction: schemas are the source and types come from them (`export type SignInRequest = z.infer<typeof SignInRequestSchema>`). To respect the folder order, allow `types` to import `schemas` only with `import type`, or move the `z.infer` to `schemas/` and leave in `types/` only the types that have no schema. Fix the ADR 0015 table and add `errors/` (and `kit/` for `@contracts/platform`).

#### BE-09 · Medium · Hexagonal architecture / Clean code · `classifyFailure` knows every provider and its AWS rule contradicts the adapter's

- `backend/libs/platform/primitives/src/lib/failure.ts:10-24` (Node and undici network codes), `:27-35` (Postgres SQLSTATE), `:45-62` (`AWS_TRANSIENT_NAMES`, SDK v3 exception names), `:64-66` (HTTP statuses), `:80-91` (`$retryable`, `$metadata` from the AWS SDK).
- `backend/libs/platform/adapters/aws/src/lib/aws-errors.ts:24-28`: `isRetryableAwsError` decides by `$fault !== 'client'`, so a 500 from SNS is retryable; in `primitives`, the same error without `$retryable` falls into `TRANSIENT_STATUS` (408, 425, 429, 502, 503, 504) and comes out `Permanent`.
- Three signals that overlap: `PlatformError.retryable`, `PlatformError.retryableExplicit` (`kernel/src/platform-error.ts:30-37`) and a `failureKind` property declared by hand by `PersistenceError`, `CacheError`, `InvalidArgumentError` and others, checked in that order in `failure.ts:113-126`.

What is wrong: the lowest library of the platform, on which all others depend, encodes details of Postgres, the AWS SDK and undici. It is the adapter that knows what an error from its provider means, and in the AWS case a classifier with a different rule already exists in the adapter, so the same error is retryable or not depending on who asks. The `retryable` plus `retryableExplicit` pair exists only so that `classifyFailure` knows whether to ignore the default value, and it coexists with `failureKind`, which says the same thing in more detail.

Fix: have each adapter translate its errors at the edge into a `PlatformError` with `failureKind` (persistence already does it with `PersistenceError`; aws with `transportError`), and reduce `classifyFailure` to reading `failureKind`, `AbortError`/`TimeoutError` and a generic HTTP status. Move `TRANSIENT_SQLSTATES` to `persistence` and the AWS rules to `adapters/aws`. Replace `retryable` and `retryableExplicit` with `failureKind` in `PlatformError` (with `retryable` as a derived getter if needed).

#### BE-10 · Medium · Good practices · The Valkey instrumentation instruments nothing and the traces' environment comes from `NODE_ENV`

#### BE-12 · Medium · Overengineering and dead code (two topology models)

There are two sources of truth for the topology. The one from the contracts (`@contracts/platform` `define-messaging.ts` plus `contracts-export/build-topology.ts`) is the one that feeds Terraform and LocalStack. The one from `@platform/messaging` (`TopicDef`, `QueueDef` with a fluent builder, `Route`, `RetryPolicy`, abstract class `Topology`) is kept whole, and at runtime it is only used through `topologyFromContracts`, which translates one into the other.

- `messaging/src/lib/topology/topology.ts:86` "Canonical JSON export of a topology, consumed by Terraform, local setup and docs" and `:323` `toJSON()`: false, Terraform reads `topology.json` from `build-topology.ts`; `toJSON` and `TopologyDocument` are only used in `topology.spec.ts`.
- `topology.ts:128-129` "Single source of truth for routing. Subclass it and declare topics, queues and routes": no production code subclasses it outside `ContractTopology`.
- `contracts-export/src/build-topology.ts:19-23` redeclares `enum TargetKind` "matches `TargetKind` from `@platform/messaging`", and `:141-143` writes `maxAttempts` twice (root and `retry`).

Fix: leave the contracts as the only definition. Reduce `Topology` to a read-only index built from `ServiceContract[]` (routes, queues, retry policy), delete `toJSON`, `TopologyDocument` and the public `TopicDef`/`QueueDef`/`Route` builders (or keep them internal). Move `TargetKind` to `@contracts/platform` and use it on both sides.

#### BE-17 · Medium · Good practices · "Read after write" only holds within the same process

### What is good

- `SessionManager` (`packages/auth/lib/src/session_manager.dart`) handles concurrency well: a single refresh in flight, a generation counter to discard results after a logout and a serialized queue over the token store. It is worth keeping as is when extending F4.
- `ShellRuntime` rotates context, scopes, bus replay and epoch synchronously when the identity changes; `MicrofrontendScope` releases resources in reverse order and reports errors without breaking the chain.
- `ApiClient` validates the request against the contract before touching the network and validates the response before decoding; `HttpTransport` is a clean port with an adapter and test fakes.
- `AccessRule` as a sealed class with `decide` (allowed, login, step-up, denied) and `StepUpRequests`, which covers the case where go_router does not complete the `push`, are well thought out and tested.
- `contracts_gen` has a `--check` mode, formats with `dart_style`, rejects unknown JSON keys and validates permissions and roles against the enums; the sync test between catalog and ARB prevents missing messages.
- Each microfrontend's deferred chunk and `tools/check_deferred_chunks.dart` uphold the promise of not downloading the backoffice to a customer.
- `AssistantChatController` is the pattern to copy to take logic out of the screens.
- There are no abandoned `TODO`s in `lib/`, no `as dynamic` and no abused `@visibleForTesting`; the `!` are few and almost all justified.
