# Opus audit, November 12, 2026

Three read-only audits of `main` after merging F2/F3 and the Flutter front (jehernandezr/node_template#2). Everything compiles and the tests pass; these findings show up when the pieces are wired together. This document is the input for the next phase.

## Backend

### P0: they block wiring the libraries together

1. **Failure classification is inverted between internal-api and saga.** The router turns any handler exception into `ProtocolViolation` (`internal-api/router.ts:170`), so a database outage triggers compensation. Conversely, the client throws `InternalApiError` on invalid inputs or outputs (`client.ts:88,129`) and the saga treats it as transient (`saga-engine.ts:833`). Fix: a shared `classifyFailure`; the client returns `ProtocolViolation` instead of throwing.
2. **Idempotency claims without fencing in internal-api.** Taking over a lease issues no token and `complete`/`release` do not check the owner (`store.ts:84,91,106`); the lease is a fixed 30 s and is unrelated to the deadline. Fix: `claimToken` and conditional updates; lease = deadline + margin.
3. **A saga step's key changes on recovery.** The router key includes the tenant (`router.ts:137`), but the invoker receives no tenant, actor or traceparent and the instance does not store them (`invoker.ts:31`, `model.ts:31`). Fix: persist the call context in the instance and encode the key segments as a JSON array.
4. **Messaging claims have no "in progress" state.** `claim` is a boolean (`processed-message-store.ts:11`): an SQS redelivery while the first handler is still running is marked as a duplicate and deleted. Fix: the same three-state port as internal-api, with a lease greater than or equal to the visibility timeout.

### P1

5. Outbox without fencing: all replicas use the same owner and the marks ignore the lease (`outbox-relay.ts:47`, `in-memory-outbox-store.ts:86`).
6. Outbox breaks FIFO order by `groupId` when a record fails (`outbox-relay.ts:90`).
7. Sharding can revive a stale location: `invalidate` deletes the shared key and an in-flight read rewrites it (`shard-router.ts:204,292`). Fix: versioned tombstone.
8. Time budgets are disconnected between saga (25 s), client and lease; `InternalClient.call` does not take a `signal`.
9. Four different failure classification rules (resilience, messaging, router, saga).

### P2 and security

- Idempotent saga start without comparing the input (`saga-engine.ts:168`).
- `__proto__` keys collapse hashes in `input-hash.ts` and `stable-hash.ts`. Use `Object.create(null)`.
- Incomplete log redaction (`privateKey`, `jwt`, `bearer`, `session*`, `otp`, credentials inside URLs); config lacks a `secret()` type.
- Inputs without a size limit: cursor, envelope fields, idempotency key, `Retry-After`, ShardRouter maps.
- The envelope tenant is used without verification (`dispatcher.ts:188`).
- `InvalidIdError` includes the raw value; `kernel` exports test helpers in production.

### Unification (WP-A)

Confirmed: 8 libraries with their own error class, 6 clock shapes, 4 backoffs, 3 copies of `fnv1a32` and two different canonical JSONs, incompatible result types between internal-api and saga, direct `uuid` instead of `IdGenerator`, a catalog with 13 of about 60 codes, and no Nx tags.

- **Phase 0 (one agent, additions only):** `PlatformError` in kernel; new `libs/platform/primitives` with `backoff`, `hash`, `canonical-json`, `failure`, `call-outcome`, three-state `idempotency` and `deadline`; tags in every `package.json` and ESLint rules in warn mode.
- **Phase 1 (in parallel, one agent per library):** saga, internal-api, messaging, resilience, cache, sharding, the rest (bloom, criteria, config, observability) and contracts (full catalog). Each one keeps compatibility aliases.
- **Phase 2:** remove the aliases and switch the rules to error.

## Front

### High findings

1. **Stale data when the identity changes:** with a route mounted, screens keep the previous user's data and subscriptions. Central fix: `identityEpoch` in the runtime and a `KeyedSubtree` per page in `buildShellRouter`.
2. **The previous user's badge can reach the next one:** the previous lifecycle context keeps emitting after the replay is cleared. Fix: a `ShellContext.emit` that drops events after `dispose`, and synchronous cancellation on rotation.
3. **The real notifications repository is never closed:** only the fake is closed. Fix: a `ScopedResource` interface that the scope closes automatically.

### Medium findings

- One user's SnackBar visible to the next (missing `mounted` check after each `await`).
- A lifecycle that fails on startup is not retried.
- Lifecycle state shared between runtimes: use a factory.
- Unguarded subroutes: `/tasks/new` and `/tasks/:id/edit` do not require `tasksWrite`.
- The notifications fake ships in the initial bundle.

### Common conventions (WP0)

Prerequisite in `shell_core` and `ui`: identity epoch, `ShellContext.emit`, `ScopedResource`, `AccessGate`, `accessRedirect` and `context.can`, lifecycle factory, `AppPage`, `ShellChrome`, `AsyncValueView` and `showActionError`. Layout decision: each screen owns the single top bar (`AppPage`); the shell draws no bar in compact.

Then, seven agents in parallel, one per microfrontend: builder signature `(scope, {params})` without `BuildContext`, localization only inside the deferred chunk, `ScopedResource` in repositories, no `catch (_)`, `context.go` with nested routes, per-action access control and tests for the manifest, deferred boundary, scope, l10n, states and access.

### Access and MFA

Protected actions with `AccessGate`. Backoffice: read access for any platform role; saga and redrive actions only for superAdmin or support; finance only billing. The backoffice requires recent MFA with an `AccessRule.mfa(maxAge)` rule and a `/step-up` page.

### Deferred loading guarantee

A CI job that builds `flutter build web --release --source-maps` and fails if `main.dart.js.map` includes sources from `mf_*/lib/src/{data,screens,l10n}` or if any backoffice ARB text appears in `main.dart.js`. Also, an import graph test starting from `apps/web/lib/main.dart`.

## Cross-cutting: contracts, infrastructure, CI and documentation

### Contracts

The generation pipeline described in the plan does not exist yet. The access enums only exist in Dart. The catalog `messageKey` (`errors.platform.x.y`) does not match the ARB keys (`error_platform_x_y`).

Proposed design:

- Source of truth in TypeScript with zod in `libs/contracts`, per service.
- `tools/contracts-export` writes JSON, JSON Schema, AsyncAPI and the topology for Terraform.
- `front/tools/contracts_gen` generates the Dart enums and the `errorMessage`.
- `contracts:check` fails if there are differences.

### Infrastructure

- The read replica is not reachable: RDS Proxy has no reader endpoint outside Aurora.
- Without NAT, external calls are blocked: Claude API, APNs, FCM and payments. VPC endpoints are missing.
- The apps connect with the master user and there is no parameter group (`logical_replication` is missing for moving shards).
- Valkey without authentication or CMK.
- `prod.tfvars` points to the example topology and has no alarm configured.
- The Terraform lockfile only covers darwin.
- Missing modules: ECS, ALB, CloudFront with WAF, files bucket, SES, observability, and the Lambda and Fargate service modules.

### CI

Today there is a single Node job. The following is missing:

- Jobs for Flutter, Terraform, contract drift and deferred chunk verification.
- Nx cache.
- An aggregate `ci-ok` as the only required check.
- Actions pinned by SHA.
- `.flutter-version` and `.terraform-version`.

The weekly gitleaks scan will flag the `.env` from commit `a076bb9`.

### Documentation

Several sections of `docs/ARCHITECTURE.md` must be rewritten: monorepo, front, errors, contracts, infrastructure and quality. ADR 0012 is partially superseded.

Proposed new ADRs, from 0015 to 0023:

- Microfrontend contract.
- Flutter shells.
- pub workspace outside Nx.
- Lockfiles and toolchain.
- Contract export.
- Access enums per service.
- Generated topology.
- Egress without NAT.
- OpenObserve hosting.

## Suggested order

1. In parallel: WP-A phase 0 (backend), front prerequisite (shell_core and ui) and basic CI (Flutter, Terraform, `ci-ok`).
2. In parallel: WP-A phase 1 (eight agents), front WP0 (seven agents), contracts (export and Dart generator) and data and network infrastructure.
3. Documentation and ADRs, WP-A phase 2 and new infrastructure modules.
