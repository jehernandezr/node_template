## Decisions made for the fixes

### PLAT-01 · P0 · The F2 persistence library does not exist

- File: `backend/libs/platform/` (there is no `persistence` folder); `docs/ARCHITECTURE.md:388` and `:364` describe it as existing.
- Plan: section "Persistence" and ADR 0009: `libs/platform/persistence` with `BaseRepository` (findById, findMany with cursor, save, upsert, softDelete, optimistic locking by `version`), `TransactionManager` port with Unit of Work in CLS, audit columns, a `/* traceId=… tenantId=… */` comment on every SQL statement, reads to the replica and writes to the primary, `@Partitioned` with `createPartitionedTable`/`createRangePartitions`, `@Audited` with a trigger to `audit_log` and `set_config('app.actor_id' | 'app.tenant_id' | 'app.trace_id', …, true)`, `PersistenceModule.forFeature`. ### PLAT-03 · P1 · The logger throws if the context `traceId` has hyphens

- File: `backend/libs/platform/observability/src/lib/logger.ts:235`, `backend/libs/platform/observability/src/lib/trace.ts:68`, `backend/libs/platform/observability/src/lib/request-context.ts:4`.
- Plan: "Identifiers": the `traceId` is a UUIDv7 and "The response returns `x-trace-id`"; the "Errors" example shows it with hyphens (`"traceId": "0193f1c2-..."`). A log must never bring down the request.
- Code: `RequestContextData.traceId` is an unvalidated `string`. `JsonLogger.write` calls `toDisplayTraceId(ctx.traceId)`, which throws `RangeError` if it does not receive 32 hex characters. Verified: `RequestContext.run({ traceId: '0193f1c2-0000-7000-8000-000000000001', … }, () => log.info('hola'))` throws `RangeError: Invalid trace id: 0193f1c2-…`. Any middleware that stores the hyphenated format (the one the plan shows to the client) makes every `log.*` of the request fail. Also, the error message copies the received value, which can come from an external header (`trace.ts:32,35,68`).
- Fix: in `logger.ts`, normalize without throwing (accept 32 hex or a hyphenated UUID; if it does not match, write `trace_id` as absent and a field `trace_id_invalid: true`). In `RequestContext.run`, validate and normalize `traceId` to 32 hex once. Remove the raw value from the `RangeError` messages in `trace.ts`. Add a test in `logger.spec.ts` that a malformed context does not throw.

### PLAT-05 · P1 · A retryable `DomainError` is stored as the final idempotency result

- File: `backend/libs/platform/primitives/src/lib/call-outcome.ts:123`; `backend/libs/platform/kernel/src/domain-error.ts:8`.
- Plan: "Errors" (the catalog declares whether a code can be retried) and "Consistency between services" (retries in the client). `DomainErrorOptions.retryable` exists for "a concurrency conflict", and the identity catalog already declares `TokenStalePermissions` with `retryable: true`.
- Code: `CallOutcome.fromError` turns every `DomainError` into `business-error` before consulting `classifyFailure`. `business-error` is final (`isFinalOutcome`), so the internal-api router stores it with `complete` in the idempotency store (`internal-api/src/lib/router.ts:266-275`) and every retry with the same key receives the same conflict forever. Verified: a `DomainError` with `retryable: true` gives `kind: business-error`, `final: true`, while `classifyFailure` marks it `transient`.
- Fix: in `call-outcome.ts`, if `error instanceof DomainError && error.retryable`, return `transientFailure(error.code, { cause: error })` (not final, releases the claim). Add the case to `call-outcome.spec.ts`.

### PLAT-06 · P1 · The `@platform/criteria` cursors violate the pagination contract

- File: `backend/libs/platform/criteria/src/lib/cursor.ts:14,80-82`, `backend/libs/platform/criteria/src/lib/validation.ts:5`; contract in `backend/libs/contracts/platform/src/constants/pagination.constants.ts:6-10`.
- Plan: "Persistence": `findMany(criteria, cursor)`; ADR 0015: the server and the client validate against the contract.
- Code: `encodeCursor` produces up to 2048 characters and, with `secret`, the format `payload.signature`. The contract (`CursorSchema`, used by `pageOf` in every paginated response) accepts at most 512 characters and the pattern `^[A-Za-z0-9_-]+$`, without a dot. A signed cursor always breaks the response schema and the client rejects it on validation. Same with the limit: `MAX_LIMIT = 1000` versus `Pagination.maxLimit = 100`. In addition, there are two implementations of the cursor and the page (`criteria/src/lib/cursor.ts` and `page.ts` versus `shared/utils/src/cursor.ts`), with different rules (the `shared/utils` one does not support signing or check the canonical form).
- Fix: in `criteria`, take `MAX_CURSOR_LENGTH` and `MAX_LIMIT` from `Pagination` in `@contracts/platform` and keep the signed cursor within the contract alphabet: concatenate the signature bytes to the payload before encoding in base64url, or widen `cursorPattern` to `^[A-Za-z0-9_-]+(\.[A-Za-z0-9_-]+)?$` in the contract and regenerate the Dart. Keep a single implementation of the cursor and `Page` (the `criteria` one) and have `shared/utils` re-export it or disappear. Add a test that passes a signed cursor through `CursorSchema`.

### PLAT-08 · P2 · `classifyFailure` never looks at the cause of a `PlatformError` without `failureKind`

- File: `backend/libs/platform/kernel/src/platform-error.ts:43`, `backend/libs/platform/primitives/src/lib/failure.ts:123`.

### PLAT-11 · P2 · `ConsistentHashStrategy` rebuilds the ring every time tenants of the same group alternate

- File: `backend/libs/platform/sharding/src/lib/sharding-strategy.ts:62`.
- Plan: "Sharding": consistent hashing over the key within the group, with no hot shard.

### PLAT-13 · P2 · Sharding: `ShardStrategy`, `ShardKeyResolver` and cross-process invalidation are missing

- File: `backend/libs/platform/sharding/src/lib/types.ts:2-6`, `backend/libs/platform/sharding/src/lib/shard-router.ts:42,306`, `backend/libs/platform/sharding/src/lib/placement-policy.ts:19`.
- Plan: "Sharding": `PersistenceModule.forFeature({ sharding: { strategy: ShardStrategy.Directory, key: ShardKey.User } })`; custom key "with a `ShardKeyResolver`"; `ShardPlacementPolicy` policy; when the directory changes "`PlatformEvent.ShardDirectoryChanged` is published".
- Code: there is no `ShardStrategy` enum (the strategies are classes without a declarative name); `ShardKey.Custom` exists but there is no `ShardKeyResolver`; the policy is called `PlacementPolicy`/`LeastLoadedPlacementPolicy`; `ShardDirectoryChanged` does not appear in the code. ### P1

#### F3-01 · P1 · The internal API router does not store the result in the same transaction as the effects

- File: `backend/libs/platform/internal-api/src/lib/router.ts:38-57` (options) and `:256-283` (`execute`).
- Plan, "Contracts and internal API", rules: "the server stores the key and the result in `processed_operations` within the same transaction and returns the stored result if the call is repeated". ADR 0008, "Protocol of each step": "The effect happens only once". The port itself requires it (`store.ts:13-19`: "A production store writes `complete` in the same unit of work as the handler's side effects").
- Code: `execute` calls `route.handler(input, meta)` and then, outside any unit of work, `this.processed.complete(...)`. `InternalRouterOptions` has no hook to wrap claim, handler and `complete` in a transaction. With a persistent store, if the process dies between the handler's commit and `complete`, the claim stays `in-progress`, the lease expires and the saga retry (same key) runs the handler again: duplicated effect. `MessageDispatcher` did solve this with `runInContext` (`message-dispatcher.ts:139-145`, wraps claim, handler and complete); the router fell behind.
- Fix: add `runInUnitOfWork?: <T>(fn: () => Promise<T>) => Promise<T>` to `InternalRouterOptions` and run the handler and `processed.complete` inside it (the claim can go before, in its own short transaction). Document that the persistent store must use that unit of work's connection. Test in `router.spec.ts`: a `complete` that fails inside the unit of work rolls back the simulated effect and the retry applies it only once.

#### F3-02 · P1 · Sagas do not take the compensation from the contract or validate it at startup

- Files: `backend/libs/platform/saga/src/lib/definition/saga-flow.ts:5-13` (`OperationRef`) and `:139-158` (`compile`); `backend/libs/platform/saga/src/lib/engine/saga-engine.ts:83-86` and `:1037-1046` (lazy `compile`).
- Plan, "Sagas": "Each step references the operation's contract class. The compensation comes from the contract's `compensatedBy` [...] Renaming an operation breaks the build."
