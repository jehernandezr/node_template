# Persistence with TypeORM

The ORM is TypeORM on PostgreSQL. Use its capabilities (entities, `DataSource`, `EntityManager`, `QueryBuilder`, migrations), without replacing them with hand-written SQL or a custom runner. `@platform/persistence` is a thin layer on top: transactions, tenant context, sharding, auditing and the repository base.

## Entities

- They live in `modules/<m>/infrastructure/persistence/entities/<name>.entity.ts`. They belong to infrastructure: the domain never imports them and they never leave `infrastructure/`. <!-- id: backend-persistence-typeorm.1 -->
- `@PrimaryColumn('uuid')` with the UUIDv7 the application generates (`IdGenerator`). Never autoincrement ids or ids generated by the database. <!-- id: backend-persistence-typeorm.2 -->
- Auditing, `@VersionColumn` and `@DeleteDateColumn` come from a base entity in `@platform/persistence`. <!-- id: backend-persistence-typeorm.3 -->
- Instants in `timestamptz`. Money in `bigint` of the minor unit. States as a TypeScript `enum` stored in `varchar` with a `CHECK`, not as a PostgreSQL `ENUM` type (altering it is expensive). <!-- id: backend-persistence-typeorm.4 -->
- Columns with an explicit `snake_case` name, explicit nullability (`nullable: false`) and lengths on `varchar`. <!-- id: backend-persistence-typeorm.5 -->
- Relations: declare only what is used. `lazy` and `eager` are forbidden: loading is always explicit. References between aggregates are id columns, not a navigable `@ManyToOne`. <!-- id: backend-persistence-typeorm.6 -->
- Every entity declares its indexes (`@Index`) next to the column. See `references/queries-and-indexes.md`. <!-- id: backend-persistence-typeorm.7 -->
- `synchronize` always `false`, in every environment and in tests. <!-- id: backend-persistence-typeorm.8 -->

## Repositories and mappers

- The domain declares the port (`TaskRepository`). Infrastructure implements it with `TypeOrmTaskRepository`, which extends `TenantIsolatedRepository` (the only repository base, [ADR 0037](../../../docs/adr/0037-composition-shared-platform-pieces-and-domain-events.md)) and maps with a `TaskMapper`. Each query filters by `this.tenantId()`, the tenant of the `ShardScope` the use case opened with `ShardScopes.inTenantShard`; without it the repository fails closed. User data without a tenant column uses identity's `UserShardRepository` pattern inside `ShardScopes.inUserShard`. <!-- id: backend-persistence-typeorm.9 -->
- Pages are keyset pages written by the repository. The cursor comes from the injected `IdCursor`, or from a cursor class of the service built on the injected `CursorCodec`. <!-- id: backend-persistence-typeorm.10 -->
- Saving is per whole aggregate. The mapper rebuilds with `User.rehydrate(...)`, never with the public constructor or with `Object.assign`. <!-- id: backend-persistence-typeorm.11 -->
- The repository gets the `EntityManager` of the current transaction from `@platform/persistence`. It never opens connections or a `QueryRunner` on its own, nor uses the global `dataSource.manager` inside a transaction (it would step outside it). <!-- id: backend-persistence-typeorm.12 -->
- A repository method expresses a business need (`findActiveByEmail`), not a generic filter. <!-- id: backend-persistence-typeorm.13 -->
- Database errors are translated to domain errors inside the repository (`23505` to the uniqueness rule). Those with no business meaning are translated by `PersistenceErrorTranslator` to `PersistenceError`, classified by `PostgresFailureClassifier`. See `backend-errors`. <!-- id: backend-persistence-typeorm.14 -->
- Query reads return read DTOs with a `select` of the needed columns, not entities. <!-- id: backend-persistence-typeorm.15 -->

Example in `references/examples.md`, section "Repositories and mappers".

## Transactions and concurrency

- The use case opens it with the `TransactionManager` port (Unit of Work). One use case is one transaction. The outbox is written in the same one. <!-- id: backend-persistence-typeorm.16 -->
- Inside the transaction, only the database: no HTTP calls, SNS, email or waits. External effects go in `afterCommit`. <!-- id: backend-persistence-typeorm.17 -->
- Transactions do not cross shards (`PLATFORM.SHARDING.CROSS_SHARD_TX`). <!-- id: backend-persistence-typeorm.18 -->
- Default concurrency: optimistic locking with `@VersionColumn`. An `UPDATE ... WHERE version = $n` that affects no rows throws a retryable `ConcurrencyConflictError`. <!-- id: backend-persistence-typeorm.19 -->
- Pessimistic locking (`FOR UPDATE`, `SKIP LOCKED` for queues) only where conflict is expected and frequent, such as balances or batch consumption. <!-- id: backend-persistence-typeorm.20 -->
- Details on isolation, retries and examples in `references/transactions-and-concurrency.md`. <!-- id: backend-persistence-typeorm.21 -->

## Migrations

- Each service has `backend/apps/<service>/migrations/` with `shard/` and `catalog/` subfolders. <!-- id: backend-persistence-typeorm.22 -->
- They are generated with the CLI from the entities: `pnpm nx run <service>:migration-generate --name=<Name>`. Review them line by line before the commit: the generator does not understand expand/contract, does not use `CONCURRENTLY` and may propose a `DROP` and `ADD` where you want a `RENAME`. <!-- id: backend-persistence-typeorm.23 -->
- They are applied with `migration-run` and reverted with `migration-revert`. These commands load JavaScript, so they run on the build output. <!-- id: backend-persistence-typeorm.24 -->
- On deploy, the app's `migrate` binary calls `dataSource.runMigrations()` under a `pg_advisory_lock`, so two tasks do not apply them at once. It runs as a pre-deploy step, not at the startup of each instance (`migrationsRun: false`). <!-- id: backend-persistence-typeorm.25 -->
- A migration already applied in an environment is not edited: add another one. Each has `up` and `down`, or declares it is irreversible. <!-- id: backend-persistence-typeorm.26 -->
- Schema and data go in separate migrations. A backfill runs in batches, never a single `UPDATE`. <!-- id: backend-persistence-typeorm.27 -->
- Backward-compatible changes: expand and contract. Core rule: app version N and N+1 run at the same time against the same schema during the deploy. <!-- id: backend-persistence-typeorm.28 -->
- Integration tests apply the real migrations on a clean container and check that the resulting schema matches the entities (generating again produces no changes). <!-- id: backend-persistence-typeorm.29 -->
- Operation-by-operation guide in `references/zero-downtime-migrations.md`. <!-- id: backend-persistence-typeorm.30 -->

## Sharding

- There is one `DataSource` per logical shard and one for the catalog. Routing picks the `DataSource` by tenant or user (ADR 0010 and 0023). <!-- id: backend-persistence-typeorm.31 -->
- Every query declares its key (`ShardKey`). Without a key it fails with `PLATFORM.SHARDING.KEY_MISSING`. <!-- id: backend-persistence-typeorm.32 -->
- Reads go to the replica except inside a transaction or when you need to read what was just committed (`readPrimary`). <!-- id: backend-persistence-typeorm.33 -->
- A cross-shard query is explicit, with a concurrency limit and a possibly partial result. <!-- id: backend-persistence-typeorm.34 -->

## Before integrating

```
- [ ] Entity with @Index for each new query by filter or order
- [ ] No N+1: no queries inside loops, relations loaded in one query
- [ ] Migration generated, reviewed and with down
- [ ] Migration compatible with the previous app version
- [ ] Mapper with a round-trip test
- [ ] Repository integration test against real PostgreSQL
```

## Current decision

Persistence is TypeORM with `@platform/persistence` ([ADR 0024](../../../docs/adr/0024-typeorm-persistence-sharding-persistent-sagas.md)), which replaces the custom layer over `pg` from ADR 0009. The platform provides shard routing, the single-shard transaction (`ShardScope`, error `CROSS_SHARD_TX`), replica reads and migrations per shard and catalog; the service writes entities, mappers, repositories that extend `TenantIsolatedRepository` and migrations. The platform tables (outbox, processed messages, idempotency, shard directory and saga log) live in `@platform/adapters-postgres`.

Repository integration tests use Testcontainers with `ContainerRuntime` and `INTEGRATION_TESTS=require` in CI (see `backend-testing`).
